## 0. The three confirmations, up front

- **No real merchant data.** Every row in the database was generated by
  `src/seed/seed.ts`. Two invented workspaces — "Alpha Kirana Store (synthetic)"
  and "Beta Cloth House (synthetic)" — with invented names, phone numbers and

  server, `http://127.0.0.1:4000`. The process **refuses to start** against a
  non-loopback `DATABASE_URL`.
- **No web integration.** `esytol` does not import, reference or call
  `vyora-api`. Verified by grep across `app/`, `lib/`, `features/`, `.github/`,
  `next.config.ts` and `package.json` — zero matches.

## 1. Local database path — native PostgreSQL, not Docker

**Docker was attempted first, as instructed, and failed.**

```
winget install --id Docker.DockerDesktop     → Successfully installed (4.85.0)
docker --version                             → Docker version 29.6.2
Docker Desktop launch                        → engine never became ready
```

The founder confirmed the dialog: _"Docker Desktop failed to start because
virtualisation support wasn't detected."_ Independently corroborated —
`Win32_ComputerSystem.HypervisorPresent` is `False`, and `docker info` still
returns `500 Internal Server Error` from the Linux engine pipe.

This machine cannot run Docker without enabling Hyper-V or WSL2, which needs an
elevated shell and a reboot. Note that VT-x _is_ enabled in firmware
(`VirtualizationFirmwareEnabled = True`, recorded in VYORA-PLATFORM-002); the
missing pieces are the Windows optional features, not the CPU.

**Fallback taken — rule 3 of the prerequisite gate.**

`winget install PostgreSQL.PostgreSQL.16` was attempted and its UAC prompt was
cancelled (`0x800704c7`). Rather than retry an interactive installer, the
official EnterpriseDB **portable binaries** were used: the same native
PostgreSQL 16, no administrator rights, no Windows service, and a cluster whose
port and data directory are under our control — which suits a synthetic
development database better than a machine-wide install.

```

→ C:\Users\dell\pgsql16
initdb -D C:\Users\dell\pgsql16\pgdata -U postgres -E UTF8 --locale=C
```

## 6. Defects found and fixed during implementation

Recorded because each was invisible to review and only a test caught it.

| Defect                                                                                  | Consequence had it shipped                                                                                             |
| --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Duplicate detection compared serialised JSON, but `jsonb` does not preserve key order   | Genuine duplicates misread as `EVENT_ID_CONFLICT`; clients would quarantine good events and outboxes would never drain |
| `recorded_at` stored microseconds while cursors round-trip through millisecond ISO-8601 | The last event of every page re-served forever — an infinite pull loop                                                 |
| Windows-only entrypoint check (`"file://" + argv[1]`) never matched                     | `db:migrate` and `db:seed` exited 0 having done nothing, indistinguishable from success                                |
| Unexpected errors were never logged                                                     | An `INTERNAL_ERROR` nobody can diagnose; this is what hid the defect above                                             |

The first two would each have corrupted or stalled a merchant's sync in ways
that look like "the app is broken" with no useful signal.

## 7. Repository isolation

`vyora-api/` has its own `package.json` and `package-lock.json`. No workspaces,
no Turbo, no Nx, no import rewrites. The root `package-lock.json` is byte-identical.

**Two root files were changed**, both narrowly and neither affecting the build
or deployment:

| File               | Change                                                 | Why                                                                                                                                                                                                       |
| ------------------ | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tsconfig.json`    | `exclude: [..., "vyora-api"]`                          | The root config had `include: ["**/*.ts"]`, so it type-checked the API as well. Two tsconfigs compiling the same files with different module settings is wrong regardless of whether it currently passes. |
| `vitest.config.ts` | `exclude: [...configDefaults.exclude, "vyora-api/**"]` | The root Vitest had no `include`/`exclude` and swept `vyora-api/tests/**`, running them under jsdom with file parallelism against a shared database. They failed for reasons unrelated to the web app.    |

Neither file is read by `next build` in a way that touches `app/`, and neither
is used by Vercel. Nothing in `vercel.json`, `.github/workflows/`,
`next.config.ts` or `package.json` was modified.

**No CI hook was added.** The milestone permits adding one "after confirming
they do not alter the existing web deployment" — but this API needs a live
PostgreSQL service in CI, and adding that to the existing `ci.yml` would change
a workflow that currently gates production deploys. Leaving the web pipeline
untouched was the safer reading. Running the API suite in CI is a Phase B
decision with its own workflow file.

## 9. Known limitations

**Implementation**

- Bearer tokens are rows in `access_tokens`, not real JWTs. The identity
  provider is deferred to Phase E; the contract only requires "a validated token
  resolves to a workspace".
- No rate limiting. `429`/`RATE_LIMITED` are specified in the contract but not
  enforced.
- No projection-rebuild command. The log is authoritative and rebuild is
  possible in principle, but there is no operator command for it yet.
- No server-side log compaction, and the `events` table only grows.
- `GET /parties` keyset-paginates by `party_id`, so ordering is by id rather
  than by name or activity.
- `OCCURRED_AT_OUT_OF_RANGE` and `AGGREGATE_MISMATCH` are defined rejection
  reasons that nothing currently emits — no plausible-clock or aggregate
  cross-check is implemented.
- `ContactDeleted` tombstones are applied by sync but no endpoint issues one.
- Devices self-register implicitly; there is no de-registration path.

**Environment**

- Docker is unusable on this machine (§1). Anyone reproducing this on a machine
  with virtualisation available should prefer Docker Compose; the schema and
  connection string are unchanged either way.
- The PostgreSQL cluster is started manually and is not a Windows service, so it
  does not survive a reboot.
- 2 CPU cores means the test suite is slow and sensitive to load — see §10.

**Deferred decisions, untouched by this milestone**

The four from `openapi-design.md` §6 remain open: the delete/create race, legal
erasure versus immutable history, whether snapshots ever sync, and the real
onboarding/authentication provider. None was solved in code.

## 10. A real constraint worth knowing: this machine has 2 cores

While PostgreSQL was running, the root `npm run validate` failed **twice**, both
times on the same pre-existing test:

```
FAIL  tests/lib/emi.test.ts > 1000 deterministic scenarios
Error: Test timed out in 30000ms.
```

This is **not** caused by any change in this milestone, and it was worth proving
rather than assuming:

- run alone, that file passes — but its heavy test takes **32.8 s of a 30 s
  budget's worth of work**, so it has almost no headroom;
- with the PostgreSQL cluster **stopped**, the full root validate passes cleanly
  (§8);
- the only root files this milestone touched are `tsconfig.json` and
  `vitest.config.ts`, and neither affects that test's runtime.

So the cause is CPU contention: an i3-6006U with 2 physical cores cannot run a
PostgreSQL cluster and a 360,000-iteration reconciliation test at the same time.

**Practical consequence:** stop the local PostgreSQL cluster before running the
root `npm run validate` on this machine, or run the two suites at different
times. CI is unaffected — the API suite does not run there (§7).

**Worth flagging separately:** `tests/lib/emi.test.ts` is one slow machine away
from failing on its own merits. It is a pre-existing fragility, out of scope
here, but it will keep costing time until that test is split or given an
explicit per-test timeout.
